# 可持续对话分析 - 逻辑设计文档

## 1. 系统概述

### 1.1 设计目标

将组件分析器从"自动分析模式"重构为"对话式分析模式"，模仿 Cursor/Kiro 等 Agent IDE 的交互体验，让用户能够：
- 选择组件后自主决定何时发起分析
- 通过自然语言提问深入了解组件细节
- 在上下文中进行多轮对话

### 1.2 核心交互流程

```
┌─────────────────────────────────────────────────────────────┐
│  1. 用户点击选择图标                                          │
│         ↓                                                    │
│  2. 进入组件选择模式（页面高亮）                               │
│         ↓                                                    │
│  3. 用户点击页面组件                                          │
│         ↓                                                    │
│  4. 组件名称显示在输入框上方（带关闭按钮）                      │
│         ↓                                                    │
│  5. 用户输入问题（可选）                                       │
│         ↓                                                    │
│  6. 点击发送按钮                                              │
│         ↓                                                    │
│  7. AI 分析并返回结果                                         │
│         ↓                                                    │
│  8. 用户可继续提问（多轮对话）                                 │
└─────────────────────────────────────────────────────────────┘
```

## 3. 数据模型设计

### 3.1 核心数据结构

**ChatMessage - 对话消息**
- id: 唯一标识
- role: 'user' | 'assistant' | 'system'
- content: 消息内容
- timestamp: 时间戳
- componentRef: 关联的组件信息（可选）

**SelectedComponent - 已选组件**
- name: 组件名称
- filePath: 文件路径
- githubUrl: GitHub 链接
- code: 组件源代码
- line: 行号

**ChatSession - 对话会话**
- id: 会话 ID
- component: 当前组件
- messages: 消息列表
- tokenUsage: token 使用统计
- createdAt: 创建时间
- updatedAt: 更新时间

### 3.2 状态管理结构

**PanelState - 面板状态**
- status: 'idle' | 'selecting' | 'ready' | 'loading' | 'chatting'
- selectedComponent: 已选组件（可为空）
- messages: 消息列表
- inputValue: 输入框内容
- tokenUsage: 当前 token 使用量
- tokenLimit: token 上限
- error: 错误信息（可为空）

## 4. 后端 API 设计

### 4.1 Chat API 端点

**POST /api/chat**

请求体结构：
- sessionId: 会话标识
- question: 用户问题（可为空，空则使用默认分析）
- component: 组件信息（首次请求必须）
  - name: 组件名称
  - code: 源代码
  - filePath: 文件路径
- history: 历史消息列表（最近 N 条）

响应体结构：
- success: 是否成功
- answer: AI 回复内容
- tokenUsage: 本次请求 token 消耗
  - prompt: 输入 token
  - completion: 输出 token
  - total: 总计
- suggestedQuestions: 推荐问题列表（可选）


### 4.2 上下文构建逻辑

```
┌─────────────────────────────────────────────────────────────┐
│                    Prompt 构建流程                           │
├─────────────────────────────────────────────────────────────┤
│  1. System Prompt (固定)                                     │
│     - 角色定义：你是一位专业的前端组件分析助手                  │
│     - 输出要求：使用简洁易懂的语言，面向非技术人员              │
│                                                              │
│  2. Component Context (首次/组件变更时)                       │
│     - 组件名称                                               │
│     - 组件源代码（截断至 maxCodeLength）                      │
│     - 文件路径                                               │
│                                                              │
│  3. History Context (每次请求)                               │
│     - 最近 N 轮对话                                          │
│     - 按时间顺序排列                                         │
│                                                              │
│  4. User Question (当前请求)                                 │
│     - 用户输入的问题                                         │
│     - 或默认分析指令                                         │
└─────────────────────────────────────────────────────────────┘
```

### 4.3 Token 限制策略

**Qwen 模型上下文限制：**
- qwen-turbo: 8,192 tokens
- qwen-plus: 32,768 tokens

**Token 分配策略：**
- System Prompt: ~200 tokens (固定)
- Component Code: ~4,000 tokens (可配置上限)
- History: ~2,000 tokens (动态调整)
- User Question: ~500 tokens
- Response Buffer: ~1,500 tokens

**超限处理逻辑：**
1. 计算当前请求总 token 数
2. 如果超限，首先截断历史对话（保留最近 3 轮）
3. 如果仍超限，截断组件代码
4. 如果仍超限，返回错误提示用户重新选择组件

## 5. 消息传递设计

### 5.1 消息类型定义

**Content Script → Background Script:**
- CHAT_SEND_MESSAGE: 发送对话消息
- CHAT_CLEAR_SESSION: 清空会话
- CHAT_GET_TOKEN_USAGE: 获取 token 使用量

**Background Script → Content Script:**
- CHAT_MESSAGE_RESPONSE: 对话响应
- CHAT_MESSAGE_ERROR: 错误响应
- CHAT_TOKEN_WARNING: token 超限警告

### 5.2 消息流程

```
Content Script                Background Script              Backend
     │                              │                           │
     │  CHAT_SEND_MESSAGE           │                           │
     │ ─────────────────────────────>                           │
     │  {question, component}       │                           │
     │                              │   POST /api/chat          │
     │                              │ ─────────────────────────>│
     │                              │                           │
     │                              │   {answer, tokenUsage}    │
     │                              │ <─────────────────────────│

     │ <─────────────────────────────                           │
     │  {answer, tokenUsage}        │                           │
     │                              │                           │
```

## 7. Prompt 工程设计

### 7.1 System Prompt

**角色定义：**
- 身份：专业的前端组件分析助手
- 目标用户：产品经理、测试人员、业务人员
- 输出风格：简洁易懂，避免技术术语

**输出要求：**
- 使用中文回答
- 使用 Markdown 格式
- 重点突出，条理清晰
- 不提及代码变量名、函数名

### 7.2 默认分析 Prompt

当用户未输入问题时，使用默认分析指令：
- 请分析这个组件的功能概述
- 说明组件会显示什么内容
- 列出组件可能的状态
- 描述用户可以进行的操作

### 7.3 自定义问题 Prompt

当用户输入问题时：
- 基于组件代码上下文回答用户问题
- 如果问题与组件无关，礼貌提示
- 如果需要更多信息，主动询问

### 7.4 上下文引用 Prompt

在多轮对话中：
- 引用之前的对话内容
- 保持回答的连贯性
- 避免重复已说过的内容

## 8. 错误处理设计

### 8.1 前端错误处理

| 错误类型 | 处理方式 |
|----------|----------|
| 网络错误 | 显示重试按钮 |
| 超时错误 | 显示超时提示，建议重试 |
| Token 超限 | 显示警告，建议重新选择组件 |
| 组件解析失败 | 显示错误提示，建议选择其他组件 |

### 8.2 后端错误处理

| 错误类型 | HTTP 状态码 | 响应内容 |
|----------|-------------|----------|
| 参数缺失 | 400 | 具体缺失字段 |
| AI 服务错误 | 502 | 服务暂时不可用 |
| Token 超限 | 413 | 上下文过长提示 |
| 内部错误 | 500 | 通用错误信息 |

## 9. 性能优化设计

### 9.1 前端优化

- 消息列表使用虚拟滚动（消息超过 50 条时）
- 输入框防抖处理（300ms）
- 组件代码懒加载

### 9.2 后端优化

- 组件代码缓存（避免重复获取）
- 会话上下文缓存（减少重复计算）
- 响应流式输出（可选，提升体验）
