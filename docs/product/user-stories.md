# C-Pointer 用户故事

本文档保留首版所需的完整用户故事分组，供后续 MVP 裁剪。

## Epic 1：插件入口与环境识别

### US-1.1 支持页面识别

作为用户，我希望插件只在支持的 Web 或 POS 测试环境中可用，以便避免在无关页面误触发。

验收标准：

- 插件能识别当前页面是否属于支持站点。
- 不支持页面时明确提示不可分析。
- 支持页面时插件直接进入可用状态。

优先级：P0

### US-1.2 激活分析模式

作为用户，我希望通过点击插件入口进入组件选择模式，以便开始分析页面组件。

验收标准：

- 用户可以显式进入选择模式。
- 进入后页面有明显视觉反馈。
- 用户可以随时退出选择模式。

优先级：P0

### US-1.3 识别 workspace

作为用户，我希望知道当前分析的是 Web 还是 POS，以便结果不混淆。

验收标准：

- 系统识别并显示当前 workspace。
- 结果中保留 workspace 信息。

优先级：P0

### US-1.4 识别 environment

作为用户，我希望系统识别当前页面是 test、uat 还是 local，以便定位正确源码。

验收标准：

- 系统自动解析 environment。
- 解析失败时允许手动纠正。

优先级：P0

## Epic 2：组件选择与定位

### US-2.1 悬停预览组件

作为测试人员，我希望鼠标悬停时看到待选区域预览，以便确认选中边界。

验收标准：

- 悬停时有可见高亮。
- 高亮尽量贴近组件范围。

优先级：P0

### US-2.2 点击选中组件

作为用户，我希望点击页面区域即可选中目标组件，以便开始分析。

验收标准：

- 选中后形成当前会话。
- 选中状态可被结果面板消费。

优先级：P0

### US-2.3 向上查找最近业务组件

作为产品经理，我希望点击子节点时系统自动回溯到最近业务组件，以便结果更有意义。

验收标准：

- 点击非组件节点时可以向上回溯。
- 优先命中业务组件而不是基础 DOM。

优先级：P0

### US-2.4 支持 codeInspectorPlugin

作为系统，我希望优先消费 `codeInspectorPlugin` 的 `data-insp-path`，以便稳定定位源码。

验收标准：

- 系统能解析 `path:line:column:componentName` 结构。
- 缺失插件时给出降级提示。

优先级：P0

### US-2.5 手动纠正组件

作为开发人员，我希望在自动识别失败时手动纠正组件路径，以便继续分析。

验收标准：

- 提供手动纠正入口。
- 更正后可继续分析流程。

优先级：P1

## Epic 3：源码定位与上下文获取

### US-3.1 定位真实文件

作为开发人员，我希望系统能定位到真实源码文件和行号，以便验证分析结果。

验收标准：

- 返回文件路径。
- 尽量返回行号和列号。
- 返回定位置信度。

优先级：P0

### US-3.2 定位 GitHub 源码

作为用户，我希望系统根据页面路径信息映射到 `joyboy` 仓库中的真实源码，以便继续分析。

验收标准：

- 可以从相对路径映射到 GitHub 文件。
- 跳转失败时明确提示原因。

优先级：P0

### US-3.3 获取关键依赖文件

作为开发人员，我希望系统不仅拿到目标组件文件，还能拿到关键依赖文件，以便得到更像 Cursor/Codex 的分析效果。

验收标准：

- 补充直接 import、关键类型、service、store、domain 文件。
- 依赖补充范围可控。

优先级：P0

### US-3.4 获取页面上下文

作为测试人员，我希望系统同时记录页面 URL、workspace、environment 和组件上下文，以便分析不脱离运行场景。

验收标准：

- 页面上下文进入分析链路。
- 不采集超出必要范围的数据。

优先级：P1

## Epic 4：AI 分析

### US-4.1 生成业务概述

作为产品经理，我希望系统用业务语言解释组件做什么，以便不用先看源码。

验收标准：

- 输出业务可读摘要。
- 结论基于代码和页面上下文。

优先级：P0

### US-4.2 解释展示内容

作为用户，我希望知道这个组件展示什么信息以及业务含义，以便理解页面价值。

验收标准：

- 列出主要展示信息。
- 说明业务含义。

优先级：P0

### US-4.3 解释交互与状态

作为测试人员，我希望知道组件的交互、状态、错误态和边界条件，以便设计测试用例。

验收标准：

- 列出主要交互。
- 列出主要状态与切换条件。

优先级：P0

### US-4.4 解释接口与副作用

作为产品和测试人员，我希望知道组件依赖哪些接口或副作用，以便评估风险。

验收标准：

- 列出关键 API、导航、埋点、支付、打印等副作用。

优先级：P1

### US-4.5 解释影响范围

作为产品经理，我希望知道修改该组件可能影响哪些页面或流程，以便评估风险。

验收标准：

- 返回上游或下游影响范围。
- 标注结论置信度。

优先级：P1

## Epic 5：结果展示

### US-5.1 侧边面板展示结果

作为用户，我希望在页面侧边面板中查看结果，以便边看页面边理解组件。

验收标准：

- 面板可滚动。
- 不阻断页面正常查看。

优先级：P0

### US-5.2 分层展示结果

作为产品经理，我希望先看到结论，再选择是否展开技术细节，以便信息不过载。

验收标准：

- 默认展示摘要。
- 支持展开源码证据和技术细节。

优先级：P0

### US-5.3 展示证据信息

作为开发人员，我希望结果里包含文件路径、GitHub 链接和关键代码片段，以便验证 AI 结论。

验收标准：

- 显示源码入口。
- 显示相关代码片段。

优先级：P0

## Epic 6：追问与历史

### US-6.1 围绕当前组件继续追问

作为用户，我希望基于当前组件持续追问，以便逐步深入理解。

验收标准：

- 支持多轮问答。
- 会话保留当前组件上下文。

优先级：P0

### US-6.2 保存设备级历史

作为用户，我希望在同一浏览器或设备上保留近期会话，以便短期回看和续问。

验收标准：

- 每个设备具备独立历史。
- 可查看最近分析过的组件会话。

优先级：P0

### US-6.3 用摘要压缩长会话

作为系统，我希望在长会话中用摘要替代全部历史原文，以便控制 token 和成本。

验收标准：

- 最近几轮保留原文。
- 更早历史压缩成摘要。

优先级：P0

## Epic 7：配置与安全

### US-7.1 后端代理 GitHub 与 GPT

作为系统负责人，我希望 GitHub 访问和 GPT 调用都经过后端代理，以便保护凭证。

验收标准：

- 插件不暴露 GitHub token。
- 插件不暴露 GPT API key。

优先级：P0

### US-7.2 记录可观测信息

作为维护人员，我希望能看到分析链路中的错误和耗时，以便排查问题。

验收标准：

- 可以定位失败发生在哪个环节。
- 日志不泄露敏感源码和凭证。

优先级：P1
