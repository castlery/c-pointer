# C-Pointer 产品需求文档

## 1. 文档目的

本文件用于在清空旧实现后，重新定义 `C-Pointer` 的产品目标、适用范围、用户角色、核心流程、完整用户故事和待确认问题。

本阶段不讨论具体技术选型，不继承旧代码结构，只讨论产品需求本身。

---

## 2. 产品定义

`C-Pointer` 是一个内部浏览器插件，用于在 Castlery 的 Web 和 POS 测试环境中，帮助产品、测试、开发快速理解页面组件对应的真实业务实现。

用户在页面中打开插件后，可以选择一个组件，系统基于页面上下文、环境信息和代码仓库信息，返回该组件的业务说明、交互行为、依赖关系、风险影响和进一步问答能力。

它不是一个开发调试面板，而是一个“页面到源码到业务解释”的分析工具。

---

## 3. 背景问题

当前团队在 Web 和 POS 测试环境中存在以下问题：

- 非研发角色无法稳定定位一个页面元素对应的真实组件。
- 即使拿到组件名，也很难知道它属于哪个仓库、模块、分支、端类型。
- 产品和测试往往想理解“它做什么、有哪些状态、改动会影响哪里”，但只能依赖开发口头解释。
- 同一业务可能同时存在 Web 与 POS 两套实现，理解和比对成本高。
- 现有信息分散在页面、源码、GitHub、文档和人脑中，缺少统一入口。

---

## 4. 产品目标

### 4.1 业务目标

- 降低 PM、QA、开发理解页面组件的成本。
- 缩短“发现问题 -> 定位组件 -> 理解逻辑 -> 评估影响”的时间。
- 让 Web 和 POS 的测试环境都具备统一的组件分析入口。
- 为后续测试设计、需求评审、回归评估提供更稳定的依据。

### 4.2 用户目标

- PM 可以用业务语言理解组件作用和改动影响。
- QA 可以快速识别组件状态、交互、接口和测试边界。
- 开发可以快速定位真实源码、依赖和上下文。

### 4.3 产品成功标准

- 用户能在 3 步内完成组件选择并获得结果。
- 组件定位成功率达到可用水平，尤其是 Web/POS 测试环境中的核心业务组件。
- 分析结果能同时服务 PM、QA、开发三类角色，而不是只偏向源码阅读。
- 系统支持继续追问，而不需要用户频繁重复选组件。

---

## 5. 非目标

当前阶段不把以下内容作为首要目标：

- 直接修改线上或测试环境页面。
- 自动生成生产代码并写回仓库。
- 取代现有 IDE、DevTools 或代码搜索工具。
- 成为完整的设计系统平台或测试平台。
- 覆盖所有技术栈和所有非前端页面元素。

---

## 6. 目标用户

### 6.1 产品经理

关注点：

- 这个组件对用户来说是什么
- 会展示什么信息
- 用户能做什么操作
- 修改它会影响哪些页面或流程

### 6.2 测试人员

关注点：

- 组件有哪些状态
- 有哪些交互入口和边界条件
- 依赖哪些接口和数据
- 哪些地方需要回归验证

### 6.3 开发人员

关注点：

- 对应哪个真实组件和文件
- 所属仓库、模块、分支、环境
- 依赖链、状态管理、接口调用
- Web 和 POS 是否有差异实现

### 6.4 产品运营/业务同学

关注点：

- 页面上的某个区域承担什么业务职责
- 组件变化会不会影响转化、支付、门店流程等业务指标

---

## 7. 核心使用场景

### 场景 A：PM 在 Web 测试环境理解一个业务组件

- 打开测试页面
- 打开插件并进入选择模式
- 点击某个组件
- 查看业务概述、展示内容、交互动作、依赖模块、影响范围
- 继续追问“如果改这个，会影响哪些页面”

### 场景 B：QA 在 POS 测试环境设计测试用例

- 打开 POS 测试页面
- 选择某个组件或区域
- 查看组件状态、交互、接口、错误态、空态
- 基于结果补充测试点

### 场景 C：开发快速定位源码和上下文

- 在页面选择组件
- 插件显示真实文件路径、仓库、分支、代码片段、依赖组件
- 需要时跳转 GitHub 查看实现

### 场景 D：跨端比对

- 用户在 Web 环境选一个组件
- 再在 POS 环境选同类组件
- 系统帮助识别是否属于同一业务能力、是否存在实现差异

---

## 8. 产品原则

- 页面优先：从用户当前看到的页面出发，而不是从仓库结构出发。
- 业务优先：输出以业务解释为主，不以源码术语堆砌为主。
- 证据优先：所有解释必须能追溯到页面上下文、组件源码或仓库信息。
- 渐进披露：默认先给结论，需要时再展开源码、依赖、路径、细节。
- 一条主链：激活、选择、分析、追问必须是一条清晰主流程。
- 可扩展：产品定义必须从一开始支持 Web 和 POS，而不是为单一项目硬编码。

---

## 9. MVP 范围

### 9.1 MVP 必须覆盖

- 浏览器插件激活与退出
- 在支持页面中选择组件
- 识别基础组件上下文和真实源码路径
- 支持 Web 与 POS 两类测试环境
- 返回组件业务分析结果
- 返回文件路径、仓库链接和关键代码片段
- 支持围绕当前组件继续追问

### 9.2 MVP 可以延后

- 复杂依赖图可视化
- 跨端自动差异对比
- 导出正式测试用例
- 多模型路由和策略配置
- 团队级知识沉淀与共享空间

---

## 10. 核心概念

### 10.1 Workspace

用户当前分析的业务空间，例如：

- Web
- POS

### 10.2 Environment

用户当前页面所在环境，例如：

- local
- test
- uat

### 10.3 Target Component

用户在页面中选中的目标组件。它可以是：

- 真实 React 组件
- 可被映射到真实组件的 UI 区块
- 需要向上回溯定位的业务容器

### 10.4 Analysis Session

围绕一次组件选择建立的分析会话。会话应保留：

- 当前组件身份
- 页面上下文
- 仓库定位结果
- 已生成的分析结果
- 后续追问历史

## 11. 完整用户故事

以下用户故事按 Epic 分组，覆盖 Web 和 POS 两类核心场景。

### Epic 1：插件入口与环境识别

#### US-1.1 支持页面识别

作为用户，我希望插件只在支持的 Web 或 POS 测试环境中可用，以便避免在无关页面误触发。

验收标准：

- 插件能识别当前页面是否属于支持的业务环境。
- 不支持页面时，明确提示当前页面不可分析。
- 支持页面时，插件可直接进入可用状态。

优先级：P0

#### US-1.2 激活分析模式

作为用户，我希望通过点击插件入口进入组件选择模式，以便开始分析页面组件。

验收标准：

- 用户可显式进入选择模式。
- 进入后页面有明显的可视反馈。
- 用户可随时退出选择模式。

优先级：P0

#### US-1.3 切换工作空间

作为用户，我希望明确知道当前正在分析的是 Web 还是 POS 空间，以便结果不混淆。

验收标准：

- 系统显示当前 workspace。
- 当页面属于不同 workspace 时，系统可自动识别或提示用户确认。
- 分析结果中保留 workspace 信息。

优先级：P0

#### US-1.4 环境识别

作为用户，我希望系统识别当前页面是 local、test 还是 uat，以便正确定位对应源码和分支。

验收标准：

- 系统能自动解析环境信息。
- 分析结果中显示环境信息。
- 当环境识别失败时，允许用户手动纠正。

优先级：P0

#### US-1.5 页面权限与失败提示

作为用户，我希望在插件无法注入或页面受限时看到明确原因，以便知道下一步怎么处理。

验收标准：

- 页面不可分析时给出清晰提示。
- 区分页面不支持、权限不足、注入失败、网络异常等原因。
- 提供重试或反馈入口。

优先级：P1

### Epic 2：组件选择与定位

#### US-2.1 悬停预览组件

作为测试人员，我希望鼠标悬停时能看到待选范围预览，以便确认我选中的组件边界。

验收标准：

- 悬停时有高亮边框或遮罩。
- 边界尽量贴近可分析的组件范围。
- 移开后高亮恢复。

优先级：P0

#### US-2.2 点击选中组件

作为用户，我希望点击页面上的区域即可选中目标组件，以便开始分析。

验收标准：

- 点击后组件进入选中状态。
- 选中后不要求用户立即重新点击插件。
- 选中组件信息被持久化到当前会话。

优先级：P0

#### US-2.3 自动向上查找最近业务组件

作为产品经理，我希望当点击到基础 DOM 或子节点时，系统能自动回溯到最近的真实业务组件，以便结果有意义。

验收标准：

- 点击非组件节点时，系统尝试向上回溯。
- 优先返回业务组件而非纯基础 UI 元素。
- 无法回溯时明确告知当前命中的是不可分析节点。

优先级：P0

#### US-2.4 识别组件类型

作为开发人员，我希望系统识别这个组件属于业务组件、共享组件、设计系统组件还是未知组件，以便判断分析深度。

验收标准：

- 结果中显示组件类型标签。
- 识别逻辑可扩展，不绑定单一仓库命名。
- 未识别时显示未知并给出原因。

优先级：P0

#### US-2.5 处理复杂页面结构

作为用户，我希望插件在 iframe、shadow DOM、Portal 或嵌套区域中仍尽可能帮助定位组件，以便在真实业务页面中可用。

验收标准：

- 系统对复杂页面结构有兜底策略。
- 不支持的结构会给出清晰提示。
- 不因单个失败节点影响整个插件可用性。

优先级：P1

#### US-2.6 手动纠正组件

作为开发人员，我希望在自动识别失败时可以手动输入或选择组件路径，以便继续分析。

验收标准：

- 提供手动纠正入口。
- 用户可以输入文件路径、组件名或候选项。
- 修正后可继续分析。

优先级：P1

### Epic 3：代码身份解析

#### US-3.1 定位真实文件

作为开发人员，我希望系统把选中的页面组件映射到真实源码文件，以便快速查看实现。

验收标准：

- 返回真实文件路径或可信候选路径。
- 返回定位置信度。
- 支持行号或组件声明位置的定位。

优先级：P0

#### US-3.2 定位仓库与分支

作为用户，我希望系统知道这个组件来自哪个仓库和哪个分支，以便结果与当前环境一致。

验收标准：

- 分析结果中显示仓库与分支。
- 环境与分支映射可配置。
- 无法确定时允许用户手动切换。

优先级：P0

#### US-3.3 识别所属模块

作为产品经理，我希望知道组件属于哪个业务模块，以便判断它在业务链路中的位置。

验收标准：

- 结果中显示模块、子域或业务归属。
- 对 Web 和 POS 都适用。
- 未识别时给出未知而不是错误归类。

优先级：P0

#### US-3.4 获取运行时上下文

作为测试人员，我希望系统能结合页面上下文信息分析组件，以便结果不只基于静态文件。

验收标准：

- 系统可记录页面 URL、环境、workspace、目标元素上下文等信息。
- 这些上下文进入分析链路。
- 不采集不必要的敏感信息。

优先级：P1

#### US-3.5 支持多仓库映射

作为产品负责人，我希望一个插件能支持多个代码仓库或代码源，以便未来覆盖更多前端产品。

验收标准：

- 代码源映射不是硬编码单一仓库。
- 可以按 workspace、环境、域名或路由进行配置。
- 新增业务线时不需要重写核心产品逻辑。

优先级：P1

### Epic 4：源码获取与上下游补全

#### US-4.1 获取组件源码

作为用户，我希望系统能获取目标组件的源码，以便生成可信分析。

验收标准：

- 能获取目标组件源码。
- 获取失败时给出明确原因。
- 获取源码失败不应导致插件整体崩溃。

优先级：P0

#### US-4.2 获取相关依赖层

作为产品经理，我希望系统在必要时补充组件依赖的服务、状态或领域层代码，以便理解完整业务链路。

验收标准：

- 系统可识别与组件直接相关的依赖层。
- 默认只拉取必要上下文，避免噪音过多。
- 用户可展开查看更多依赖来源。

优先级：P0

#### US-4.3 获取子组件关系

作为开发人员，我希望看到该组件依赖了哪些关键子组件，以便理解结构与影响范围。

验收标准：

- 返回关键子组件列表。
- 区分基础组件与业务子组件。
- 支持跳转继续分析子组件。

优先级：P1

#### US-4.4 获取关键接口依赖

作为测试人员，我希望知道该组件依赖哪些接口或数据来源，以便完善测试边界。

验收标准：

- 结果中列出关键接口、服务或 selector。
- 尽量给出用途说明。
- 无法识别时明确说明未知。

优先级：P1

### Epic 5：AI 业务分析

#### US-5.1 生成业务概述

作为产品经理，我希望系统用中文业务语言解释组件做什么，以便不用先看源码。

验收标准：

- 概述面向非研发角色可读。
- 内容基于源码和上下文而不是纯猜测。
- 结论中尽量避免技术术语。

优先级：P0

#### US-5.2 解释展示内容

作为用户，我希望知道这个组件会展示哪些信息以及这些信息的业务含义，以便理解它的页面价值。

验收标准：

- 列出主要展示信息。
- 说明这些信息对用户或业务的意义。
- 区分主信息与辅助信息。

优先级：P0

#### US-5.3 解释用户交互

作为测试人员，我希望系统说明用户可以做哪些操作以及每个操作会带来什么结果，以便设计测试路径。

验收标准：

- 列出主要交互。
- 说明触发条件和业务结果。
- 尽量覆盖点击、输入、选择、提交等动作。

优先级：P0

#### US-5.4 解释状态与分支

作为测试人员，我希望知道组件有哪些状态、空态、错态和条件分支，以便补齐边界测试。

验收标准：

- 列出主要状态。
- 说明状态切换条件。
- 指出潜在异常或边界情况。

优先级：P0

#### US-5.5 解释 Props 与输入

作为开发人员，我希望看到组件的主要输入参数和用途，以便更快理解调用方式。

验收标准：

- 列出主要 props 或输入参数。
- 说明每个输入的大致作用。
- 标记必填、可选、默认值或关键依赖。

优先级：P1

#### US-5.6 解释状态管理

作为开发人员，我希望知道组件使用了哪些状态管理方式，以便理解数据流。

验收标准：

- 识别本地状态、全局状态、上下文或 URL 状态。
- 说明状态变化的触发方式。
- 尽量区分读状态和写状态。

优先级：P1

#### US-5.7 解释接口与副作用

作为产品和测试人员，我希望知道这个组件有哪些接口调用、副作用和外部依赖，以便评估风险。

验收标准：

- 列出关键 API、埋点、导航、支付、打印等副作用。
- 说明触发场景。
- 尽量使用业务语言。

优先级：P1

#### US-5.8 解释影响范围

作为产品经理，我希望知道如果修改这个组件，可能影响哪些页面、流程或关联能力，以便评估变更风险。

验收标准：

- 返回上游或下游影响范围。
- 说明影响的置信度。
- 对未知部分明确标注，而不是伪造结论。

优先级：P1

#### US-5.9 生成测试建议

作为测试人员，我希望系统给出可操作的测试关注点，以便更快开始验证。

验收标准：

- 输出测试关注点或测试建议。
- 覆盖正常流、异常流和边界情况。
- 建议与组件实际逻辑相关。

优先级：P1

### Epic 6：结果展示

#### US-6.1 在面板中查看分析结果

作为用户，我希望分析结果集中显示在一个清晰的侧边面板中，以便边看页面边理解组件。

验收标准：

- 面板支持滚动浏览。
- 分析结果有清晰结构。
- 不遮挡关键页面操作到不可用。

优先级：P0

#### US-6.2 展示证据信息

作为开发人员，我希望在结果中看到文件路径、仓库链接、代码片段和来源说明，以便验证 AI 结论。

验收标准：

- 显示文件路径和仓库跳转入口。
- 显示关键代码片段或定位信息。
- 显示结论来源或置信度。

优先级：P0

#### US-6.3 分层展示结果

作为产品经理，我希望先看到结论，再选择是否展开源码和技术细节，以便信息不过载。

验收标准：

- 默认展示高层结论。
- 支持展开技术细节。
- 支持折叠低优先级内容。

优先级：P0

#### US-6.4 查看依赖与关系

作为开发人员，我希望看到关键依赖、子组件和数据流关系，以便快速形成整体理解。

验收标准：

- 结果中可展示关键关系。
- 不要求首版必须图形化。
- 信息足够支持进一步定位。

优先级：P1

#### US-6.5 查看历史结果

作为用户，我希望在一次会话中保留最近分析过的组件结果，以便回看和对比。

验收标准：

- 当前会话内保留历史结果。
- 支持重新切回最近组件。
- 历史不会污染新会话。

优先级：P1

### Epic 7：追问与会话

#### US-7.1 围绕当前组件继续追问

作为用户，我希望在拿到初始分析结果后继续追问，以便深入理解具体细节。

验收标准：

- 用户可以直接在结果面板中继续提问。
- 系统围绕当前组件保持上下文。
- 追问不要求用户重新选组件。

优先级：P0

#### US-7.2 会话上下文可控

作为用户，我希望在需要时清空当前会话，以便开始新的组件分析。

验收标准：

- 用户可主动清空当前组件上下文。
- 清空后新问题不会混入旧组件结果。
- 清空操作有明确反馈。

优先级：P0

#### US-7.3 回答标注不确定性

作为用户，我希望当系统没有足够证据时明确说明不确定，而不是给出看似准确但不可信的答案。

验收标准：

- 回答中区分“已确认”“推断”“未知”。
- 缺少源码或上下文时明确提示。
- 不确定结论不伪装成确定事实。

优先级：P0

### Epic 8：协作与输出

#### US-8.1 复制分析结果

作为用户，我希望快速复制分析结论，以便贴到需求单、缺陷单或群聊中。

验收标准：

- 支持复制摘要或完整结果。
- 复制内容保留结构。
- 不包含不必要的噪音信息。

优先级：P1

#### US-8.2 导出结构化结果

作为测试人员，我希望导出结构化分析结果，以便后续整理测试用例或回归清单。

验收标准：

- 支持导出为易分享格式。
- 导出内容保留组件身份和环境信息。
- 导出结果可读性良好。

优先级：P1

#### US-8.3 分享源码入口

作为开发人员，我希望一键跳转源码位置，以便进一步验证和修改。

验收标准：

- 提供文件链接或代码托管平台跳转。
- 能定位到尽量准确的文件或行号。
- 跳转失败时给出明确原因。

优先级：P0

### Epic 9：配置与管理

#### US-9.1 配置支持环境

作为系统管理员，我希望配置支持的 workspace、域名、环境和代码源，以便插件服务多个业务系统。

验收标准：

- 支持按配置管理环境与代码源。
- 新增环境不需要改产品流程定义。
- 错误配置有校验机制。

优先级：P1

#### US-9.2 配置分析策略

作为管理员，我希望配置模型、上下文深度和输出策略，以便平衡成本、速度和准确率。

验收标准：

- 支持配置默认分析策略。
- 支持不同 workspace 使用不同策略。
- 用户侧无需理解复杂技术参数。

优先级：P1

#### US-9.3 记录可观测信息

作为运营或维护人员，我希望系统记录必要的运行日志和错误信息，以便排查问题。

验收标准：

- 可观测信息不泄露敏感源码和凭证。
- 能定位失败发生在哪个环节。
- 支持统计成功率和常见失败原因。

优先级：P1

### Epic 10：安全与合规

#### US-10.1 保护源码与凭证

作为系统负责人，我希望源码访问和 AI 调用都遵守内部安全边界，以便插件不会泄露敏感信息。

验收标准：

- 插件前端不暴露敏感凭证。
- 源码访问链路受控。
- 日志与导出内容遵守脱敏要求。

优先级：P0

#### US-10.2 控制数据采集范围

作为业务负责人，我希望系统只采集完成分析所需的最小信息，以便降低安全和合规风险。

验收标准：

- 仅采集与当前组件分析相关的数据。
- 敏感信息具备过滤或脱敏策略。
- 采集范围可审计。

优先级：P0

## 12. MVP 建议主流程

1. 用户打开支持页面。
2. 插件识别当前 workspace 与 environment。
3. 用户进入选择模式。
4. 用户悬停并点击目标组件。
5. 系统定位组件身份、文件路径、仓库与分支。
6. 系统获取源码和必要上下文。
7. 系统生成首屏分析结果。
8. 用户可继续追问、复制或跳转源码。

---

## 13. 关键产品决策建议

### 13.1 首版必须统一一个主交互

首版建议只有一条交互主链：

- 插件入口
- 选择模式
- 右侧结果面板
- 当前组件会话追问

不要同时保留多套 UI 模式。

### 13.2 首版先做“可信定位 + 可读解释”

首版最关键的不是图表炫技，而是：

- 选得准
- 找得到源码
- 解释得清楚

### 13.3 首版按“配置驱动的多 workspace”设计

即使第一批只落 Web 与 POS，也必须把产品定义成：

- 页面识别可配置
- 代码源映射可配置
- 环境到分支映射可配置

否则后续会反复返工。

---

## 14. 待确认问题

以下问题建议作为下一轮讨论重点：

1. `POS` 的技术形态是什么，是否与 Web 共仓、共组件体系、共路由约定。
2. 首版支持多少个站点和域名，是否只支持测试环境。
3. 组件源码是否全部可通过统一代码托管平台访问。
4. 是否存在多个前端仓库，仓库映射关系如何定义。
5. AI 输出需要偏向 PM、QA、开发中的哪一类，还是分模式输出。
6. 首版是否需要跨端差异比对，还是先只做单组件分析。
7. 首版是否要求导出结果，还是只需复制和跳转源码。
8. 哪些数据属于敏感信息，需要明确禁止进入提示词或导出内容。

---

## 15. 下一步建议

需求讨论建议按以下顺序推进：

1. 先确认 Web 与 POS 的业务边界和技术边界。
2. 再确认 MVP 用户是谁，优先服务 PM/QA 还是开发。
3. 再从以上用户故事中裁出首版 P0。
4. 最后再根据裁剪后的需求设计信息架构和技术方案。
